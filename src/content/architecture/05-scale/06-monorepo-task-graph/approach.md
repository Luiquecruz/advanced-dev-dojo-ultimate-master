1. Model the workspace as a directed graph: nodes are packages, edges go from a package to each of its dependencies. Index packages by name and precompute the reverse edges (dependents), since several questions are asked in that direction.
2. For `affectedBy`, map each changed path to its owning package with a prefix check that includes the trailing `/`, then run a breadth-first walk over the dependents. A `Set` stops the walk from visiting a package twice when two paths reach it. Sort the result so it does not depend on traversal order.
3. For `buildOrder`, run a depth-first search from each target. Memoize the level of finished packages, and keep the current visiting path to detect back edges: a package found on the path closes a cycle, and the slice of the path from it is the error message.
4. Compute levels as the longest path to a leaf: a package can start only when its slowest chain of dependencies has finished. Group packages by level and sort each group, which is the parallel schedule a task runner executes.
5. For `run`, iterate the levels in order (you may build a level with `Promise.all`). Build a canonical input string from the name, the sorted files and the dependency hashes, hash it, and check the cache before calling `build`. Record the hash of every package, hit or miss, so its dependents can include it.
6. Check the invalidation story by hand: change one file in `utils`, and only `utils` and `web` get new hashes; `config`, `design-system` and `admin` hash exactly as before and replay from the cache.
