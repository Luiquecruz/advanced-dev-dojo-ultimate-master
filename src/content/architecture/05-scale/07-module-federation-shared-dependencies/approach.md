1. Start with `satisfies`, because every decision depends on it. Translate each range into a lower bound plus "which numbers must not change": `~` freezes major and minor, `^` freezes the leftmost non-zero number, `>=` freezes nothing, an exact version freezes all three.
2. Group the declarations by module name across all containers, keeping container order. That list is both the providers (their `version`) and the consumers (their `requiredVersion`) of the module, exactly like the share scope at runtime.
3. Turn the providers into a candidate list: one entry per distinct version, remembering the first container that provided it, sorted highest first.
4. Decide per consumer. A singleton ignores ranges when choosing (the highest version wins, one copy for the page) and uses them only to report: a rejected range is a warning, or an error when the consumer asked for `strictVersion`. A non-singleton respects ranges when choosing: take the highest candidate the range accepts, or fall back to the consumer's own bundled copy.
5. Derive the summary from the per-consumer result instead of computing it separately: the distinct versions in use, highest first, are what the browser actually downloads, and the first of them names `version` and `from`.
6. Read the result like a release manager: a non-empty `loaded` list longer than one means duplicated bytes; a warning on React means hooks run against a version the remote was not tested with; an error means the remote refuses to start.
