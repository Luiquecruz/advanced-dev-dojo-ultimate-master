1. Start from the briefing, not the editor: public and indexed, current prices, one team, one web client, simple rules. Apply the simplest option per layer (SSR with hydration, feature folders, BFF data embedded plus local UI state, one deploy) and keep the table at hand.
2. Draw the request path before coding: URL → `handleRequest` → BFF → `/api/products` → view model → `renderToString` → HTML with embedded JSON → `hydrate` → interactive UI. Each file owns one step.
3. Fix the boundary first. Export `ProductList` from the feature's `index.js` and import it from there in `App.jsx`; `filterProducts` stays internal, so the feature can change it freely.
4. Shape the data in the BFF. Validate the upstream status, then map to the smallest view model the UI needs. Formatting the price on the server keeps the UI free of currency rules and makes the payload smaller.
5. Route in the server entry. Decide the status before doing work: unknown paths return 404 immediately, a BFF failure becomes 502 (a gateway problem, not a missing page), and only `/` renders the app.
6. Serialize safely. Data placed inside `<script>` is parsed as HTML first, so any `</script>` in the data would end the tag. Escaping `<` as `\u003c` keeps the JSON valid and inert.
7. Hydrate with the same input. Read the embedded JSON, pass it to the same `App`, and call `hydrateRoot` on `#root`. Same component and same props produce the same first render, so React adopts the existing nodes and attaches events.
8. Run the tests and read them as the skeleton's acceptance criteria: every layer is exercised once, end to end, before any second feature is added.
9. Write the ADRs against the code you now have, one per layer. Context states the facts, decision names what the code does (the words the tests look for are the ones you would use anyway: SSR, hydration, public API, BFF, embedded, local), consequences name what it costs. Accept each one.
10. Close with the trade-offs: list what you left out together with the trigger that would bring it in, and the risks you accept. Re-run the tests: if an ADR and the code disagree, fix whichever one is wrong.
