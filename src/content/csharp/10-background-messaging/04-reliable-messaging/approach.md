1. List the four outcomes of one delivery before writing code: already done (duplicate), done now (processed), never possible (poison), possible later (transient). Each needs different handling, and only "done now" may change the processed store.
2. Look at the order of two lines in the starter: it marks the id, then calls the handler. If the handler fails, the store already says "processed", so the fixed message an operator resubmits is skipped as a duplicate and the order is lost without an error. Marking after success is the whole difference between idempotent and lossy.
3. Keep the store outside the consumer. Two consumer instances, like two worker processes, share it through the constructor; a `HashSet` field inside the consumer would let the second instance process the message again.
4. Build the retry loop around the handler call only. A transient failure waits and tries again, the wait doubles each time, and the attempt counter decides when to give up. The tests inject `delay`, so they check the waits without sleeping.
5. Give poison messages their own `catch`, ahead of the general one: retrying data that can never be valid only delays the dead letter. Cancellation gets the opposite treatment, an exception filter that lets it escape, because a stopping consumer must neither retry nor give the message up.
