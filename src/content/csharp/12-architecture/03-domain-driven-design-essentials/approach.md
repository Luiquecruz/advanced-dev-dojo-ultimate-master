1. Start with the value object. `Money` has no identity, so a `record` gives you value equality for free; what it does not give you is validity. Put the checks where every way of creating a `Money` passes through them: the `init` accessors, which both the constructor and `with` call.
2. Write down the invariants of the aggregate before any code: the total equals the sum of the lines, an order has 1 to 10 lines when placed, quantities are positive, one currency per order, and a placed order never changes. Each public method of `Order` must keep all of them true.
3. In `AddLine`, order the work as "check everything, compute, then mutate". A method that throws halfway after changing a field leaves the aggregate in a state no rule allows, which is worse than either outcome.
4. Close every other way in. Setters are private, and `Lines` returns a read-only wrapper rather than the list itself, so the methods of `Order` are the only code that can change an order. The last test tries the back door.
5. Treat events as part of the state change: `Place` records `OrderPlaced` in the same step that changes `Status`, and `DequeueEvents` hands the caller its own copy before forgetting them. The code that saves the order (EF Core's `SaveChangesAsync` in the lesson) is what dispatches them.
