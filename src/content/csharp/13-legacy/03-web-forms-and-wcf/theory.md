# Reading Web Forms and WCF

After this lesson you can read an ASP.NET Web Forms page and a WCF service, explain why neither moves to modern .NET by recompiling, and choose what to do with each: keep a WCF contract alive with CoreWCF, call an old SOAP service from .NET 10 with the WCF client, or plan a Web Forms page as a rewrite.

You need: 05/01 (the ASP.NET Core host), 06/01 (minimal APIs and controllers), 07/05 (ADO.NET and parameterized SQL) and 13/01 and 13/02.

## Two technologies, two different problems

**WCF** (Windows Communication Foundation) is the .NET Framework stack for SOAP services. A service publishes a WSDL, an XML description of its operations, and a client is a proxy class generated from that WSDL.

**Web Forms** imitates desktop programming: buttons raise `Click` events on the server, controls remember their values between requests, and the HTML is generated by controls rather than written in templates. The page model, the state model and the controls have no equivalent in ASP.NET Core, so a Web Forms page is redesigned, not ported.

## Web Forms: pages, controls, postbacks

A page is an `.aspx` markup file plus a code-behind class:

```html
<%@ Page Language="C#" AutoEventWireup="true" CodeBehind="Products.aspx.cs" Inherits="Shop.Products" %>
<form id="form1" runat="server">
  <asp:TextBox ID="SearchBox" runat="server" />
  <asp:Button ID="SearchButton" runat="server" Text="Search" OnClick="SearchButton_Click" />
  <asp:GridView ID="ProductsGrid" runat="server" AutoGenerateColumns="true" />
</form>
```

```csharp
// .NET Framework 4.8 code (Products.aspx.cs): does not build on .NET 10
public partial class Products : System.Web.UI.Page
{
    protected void Page_Load(object sender, EventArgs e)
    {
        if (!IsPostBack)                      // first visit, not a button click
        {
            ProductsGrid.DataSource = ProductData.All();
            ProductsGrid.DataBind();
        }
    }

    protected void SearchButton_Click(object sender, EventArgs e)
    {
        ProductsGrid.DataSource = ProductData.Search(SearchBox.Text);
        ProductsGrid.DataBind();
    }
}
```

Three ideas explain most Web Forms code:

- **Postback.** The whole page is one `<form runat="server">`. Clicking the button posts the form back to the same URL, and the server raises `SearchButton_Click`.
- **View state.** Before rendering, the page serializes control state into a hidden `__VIEWSTATE` field; on the postback it restores it. That is how a `Label`'s text or a `GridView`'s rows survive a postback, and why some pages send hundreds of kilobytes of hidden data. `SearchBox.Text` is different: a `TextBox` reads its value from the posted form data (it implements `IPostBackDataHandler`), so it keeps the user's input even with view state disabled.
- **Page life cycle.** Each request runs a fixed sequence: `PreInit`, `Init`, view state and post data loaded, `Load`, then the control events (`Click`), `PreRender`, view state saved, `Render`, `Unload`. Bugs come from code in the wrong stage, such as a value set in `Init` that is overwritten when view state is restored before `Load`, or binding data on every `Load` and losing the user's input.

Also expect `.ascx` user controls, master pages (`.master`), `UpdatePanel` partial postbacks and data source controls (`SqlDataSource`) with SQL in the markup.

Web Forms is part of .NET Framework and follows its support. There is no Web Forms in ASP.NET Core. Microsoft's guidance for teams moving off it is the e-book *Blazor for ASP.NET Web Forms Developers*, because Blazor's component and event model is the closest relative; the Copilot modernization agent also lists Web Forms among the project types it helps upgrade. For a backend team, a common choice is a rewrite into an API plus whatever front end the company already uses.

## WCF: contracts, bindings, endpoints

WCF (Windows Communication Foundation) is the .NET Framework stack for SOAP and RPC services. A service is a C# interface with attributes:

```csharp
// .NET Framework 4.8 code: does not build on .NET 10 as is
[ServiceContract]
public interface IOrderService
{
    [OperationContract]
    OrderStatus GetStatus(int orderId);
}

[DataContract]
public class OrderStatus
{
    [DataMember] public int OrderId { get; set; }
    [DataMember] public string State { get; set; }
}
```

Each endpoint combines an **address** (URL), a **binding** (transport and encoding) and a **contract**, configured in `<system.serviceModel>` in `web.config` and exposed through an `.svc` file in IIS. Common bindings: `BasicHttpBinding` (SOAP 1.1 over HTTP, the interoperable one), `WSHttpBinding` (WS-* security and reliability) and `NetTcpBinding` (binary over TCP, .NET to .NET only).

## WCF on .NET 10: two different halves

**The server side is not in .NET.** The community CoreWCF project ports it to ASP.NET Core. It is a .NET Foundation project under MIT, and Microsoft publishes a support policy for it. Your contract types move almost unchanged; the hosting moves from `web.config` into code:

```csharp
// .NET 10 with the CoreWCF.Http and CoreWCF.Primitives packages
using System.Runtime.Serialization;
using CoreWCF;
using CoreWCF.Configuration;
using CoreWCF.Description;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddServiceModelServices().AddServiceModelMetadata();
builder.Services.AddSingleton<IServiceBehavior, UseRequestHeadersForMetadataAddressBehavior>();

var app = builder.Build();
app.UseServiceModel(serviceBuilder =>
{
    serviceBuilder.AddService<OrderService>();
    serviceBuilder.AddServiceEndpoint<OrderService, IOrderService>(new BasicHttpBinding(), "/OrderService.svc");
});
app.Services.GetRequiredService<ServiceMetadataBehavior>().HttpGetEnabled = true; // serves the WSDL
app.Run();

[ServiceContract]
public interface IOrderService
{
    [OperationContract]
    OrderStatus GetStatus(int orderId);
}

[DataContract]
public class OrderStatus
{
    [DataMember] public int OrderId { get; set; }
    [DataMember] public string State { get; set; } = "";
}

public class OrderService : IOrderService
{
    public OrderStatus GetStatus(int orderId) => new() { OrderId = orderId, State = "Shipped" };
}
```

CoreWCF ships packages for HTTP, NetTcp, named pipes, Unix domain sockets, MSMQ, RabbitMQ, Kafka and WebHttp. Not every WCF feature was ported, so check the bindings and security modes you use before you promise a date.

**The client side is supported by Microsoft.** The `System.ServiceModel.*` packages (WCF Client) run on .NET 10, and `dotnet-svcutil` generates the proxy from a WSDL:

```bash
dotnet tool install --global dotnet-svcutil
dotnet-svcutil https://legacy.example.com/OrderService.svc?wsdl
```

```csharp
// ... OrderServiceClient is generated into ServiceReference/Reference.cs
var client = new OrderServiceClient();
OrderStatus status = await client.GetStatusAsync(42);
```

The generated client derives from `ClientBase<T>` and exposes `Async` methods. Only reference services you trust: generated code comes from the remote metadata.

## Common mistakes

- **Promising a "port" of Web Forms pages to Razor.** Copied code-behind fails on the first `Page_Load`, `ViewState` or server control. Plan each page as a rewrite, with the business logic extracted first.
- **Treating CoreWCF as a Microsoft product.** It is a community project with Microsoft's published support policy, not Microsoft's full support. Read that policy before a contract depends on it.
- **Moving `SqlDataSource` SQL untouched.** Markup queries often concatenate input and skip review. Rewrite them as parameterized queries in the data layer.

## In practice

- **You must call an old SOAP service** from a new .NET 10 API: use the WCF client and `dotnet-svcutil`. This is the most common case and needs no server work.
- **You own a WCF service with many clients** you cannot change: move it to CoreWCF so the contract and WSDL stay the same while the host becomes ASP.NET Core.
- **You own a WCF service with few clients** you control: consider replacing it with an HTTP API (or gRPC between .NET services) as part of the migration, and keep CoreWCF only as a bridge.
- **Web Forms**: extract the business logic out of code-behind into a `netstandard2.0` library first, so the rewrite only touches the UI.
