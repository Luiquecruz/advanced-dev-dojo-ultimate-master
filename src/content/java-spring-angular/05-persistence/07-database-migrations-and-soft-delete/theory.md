# Database Migrations and Soft Delete

A schema changes as often as the code does, and every environment needs the same changes in the same order. Letting Hibernate generate the schema cannot do that safely. This lesson covers migration tools with Flyway in detail, the settings that keep Hibernate from touching a production schema, and soft delete with `@SQLDelete` and `@SQLRestriction`, including the pitfalls that surprise teams after launch.

You need: JPA and Hibernate Basics, Spring Data Repositories, Relationships, Transactions.

## Why not ddl-auto

`spring.jpa.hibernate.ddl-auto` lets Hibernate create or alter tables. `create-drop` destroys data, and `update` only adds what is missing: it never removes or renames a column and cannot move data. It also gives no history and no review. A migration tool keeps the schema as versioned scripts in source control, applies each one exactly once per database and records what ran. Use `validate` in environments with real data to check mappings at startup without changing the schema. `none` also prevents changes but performs no schema validation.

## Flyway in Spring Boot 4

Flyway applies SQL scripts in version order. Add the starter, and the database-specific module for your database; for PostgreSQL:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

Spring Boot 4 splits auto-configuration into modules, so Flyway needs its own starter. Boot runs `Flyway.migrate()` at startup, before JPA validates the schema. By default it reads scripts from `classpath:db/migration`, named `V<VERSION>__<NAME>.sql` with two underscores, such as `V1__create_course_and_lesson.sql`:

```sql
CREATE TABLE course (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title       VARCHAR(120) NOT NULL,
    level       VARCHAR(20)  NOT NULL,
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    deleted_at  TIMESTAMP WITH TIME ZONE
);
```

Flyway records each applied script and its checksum in the `flyway_schema_history` table. If you edit a script that already ran, the checksum no longer matches and the next startup fails. Never edit an applied migration: add `V2__...` that fixes it, which is called rolling forward. Liquibase is the other tool Boot supports; it describes changes in change log files (YAML, XML, JSON or SQL) and starts from `db/changelog/db.changelog-master.yaml`. Choose one tool and use it alone for the schema.

## Writing migrations that are safe to deploy

During a rolling deployment the old and new application versions run against the same database. Make changes in steps that both versions tolerate: add a nullable column first, backfill it, deploy code that writes it, and wait until all old writers and their in-flight writes have stopped. Backfill any remaining nulls before adding `NOT NULL` in a later migration. Do the same for renames: add the new column and keep old and new columns synchronized with a database trigger or an explicit compatible dual-write strategy while both application versions run. Backfill, switch reads, drain all old writers and their in-flight writes, verify consistency, deploy a version that no longer reads or writes the old column, then drain every earlier version and its in-flight operations. Only after that may a later migration remove the old column. In that migration, remove or update synchronization triggers and functions that reference it before dropping it; PostgreSQL may not track references inside string-literal function bodies, so inspect those dependencies explicitly. A one-time copy alone cannot preserve writes made afterward. Test migrations against the same database engine as production, as the project does with Testcontainers, because an in-memory database accepts different SQL.

## Soft delete

Soft delete marks a row as deleted instead of removing it, which keeps history and allows recovery. With a nullable `deleted_at` column, Hibernate can do both halves:

```java
@Entity
@SQLDelete(sql = "UPDATE course SET deleted_at = now() WHERE id = ?")
@SQLRestriction("deleted_at IS NULL")
public class Course {
    // fields as before, including: @Column(name = "deleted_at") private Instant deletedAt;
}
```

`@SQLDelete` replaces the `DELETE` that Hibernate would issue for a removal, so `repository.deleteById(id)` runs the `UPDATE`. `@SQLRestriction` appends its condition to every query on the entity, including `findById`, JPQL, derived queries and projections, and to joins and collection loads. Both are Hibernate annotations in `org.hibernate.annotations`; the older `@Where` is no longer available in Hibernate 7. Hibernate also offers `@SoftDelete`, which manages the indicator column itself and supports a timestamp strategy.

## Pitfalls

- **Bulk deletes bypass it.** A `@Modifying @Query("delete from Course c ...")` runs a real `DELETE` and ignores `@SQLDelete`. Derived `deleteBy` methods load the entities and remove them one by one, so they do soft-delete.
- **Native queries ignore the restriction.** `@SQLRestriction` applies to JPQL and entity loading, not to SQL you write yourself. Add `AND deleted_at IS NULL` by hand, and in every report that reads the table.
- **Unique constraints still see deleted rows.** A deleted course keeps its title, so creating the same title again fails. Use a partial unique index: `CREATE UNIQUE INDEX uq_course_title_active ON course (lower(title)) WHERE deleted_at IS NULL;`. PostgreSQL supports partial unique indexes.
- **Cascades need the same treatment.** Removing a course cascades to its lessons, and those rows are physically deleted unless `Lesson` has its own `@SQLDelete`.
- **Associations to deleted rows.** A lesson whose course was soft-deleted fails with `EntityNotFoundException` when it loads the course lazily, and an inner `join fetch` silently drops the lesson.
- **It is not erasure.** Personal data that a person asked you to delete must be removed or anonymized, not hidden.

Restoring a row also needs a native `UPDATE`, because the restriction hides it from entity queries.

## Common mistakes

- Running with `ddl-auto=update` in production and calling it migrations, although it cannot rename or remove anything.
- Editing a migration that already ran on another machine, which breaks the checksum there and stops startup.
- Adding `@SQLRestriction` and assuming every query is covered, including native queries and bulk deletes.
- Forgetting the partial unique index, so a deleted row blocks the creation of a new one with the same value.

## In practice

Write a migration for every schema change, review it like code and keep each one small. Keep `validate` on to catch mapping/schema mismatches at startup. To catch them during the build, run a database-backed application-context test in that build. Decide when soft-deleted rows are purged for good, with a scheduled job, so the table does not grow without limit.
