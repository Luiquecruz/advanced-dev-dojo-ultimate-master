# Capstone: Persistence and Migrations

This stage replaces the in-memory store with PostgreSQL. The schema is owned by Flyway migrations, Hibernate only validates it, courses are paged in the database and deleted softly, and integration tests run against a real PostgreSQL started by Testcontainers.

You need: Capstone: Requirements and Design, Capstone: The Spring API.

## Goal

Add a `JpaCourseStore` that implements the `CourseStore` interface from stage two, so the controller and the service do not change. Module 05 (persistence) covers JPA, Hibernate, transactions, the N+1 problem, pagination and migrations in depth; this stage applies them.

## Features

- Migrations `V1__create_schema.sql` (tables, foreign key, indexes) and a test-only `V1000__test_data.sql` with the fixed data.
- Entities `Course` and `Instructor`, a lazy many-to-one relationship, and repositories.
- Paging and sorting in SQL, with the instructor loaded in the same query.
- Soft delete through a `deleted_at` column.
- Hibernate set to `validate`, and Open Session in View turned off.

## Acceptance criteria

1. On an empty database, startup applies `V1`, and with the test location also `V1000`; `flyway_schema_history` lists both.
2. Renaming a column in an entity without a migration makes startup fail with a schema validation error.
3. `GET /api/courses?page=0&size=2` returns `Angular Signals` and `Java Basics`; the SQL log shows one select for the page, with the instructor joined, and one count select, not one query per course.
4. `DELETE /api/courses/1` answers `204`, a later `GET` of that id answers `404`, and the row still exists with `deleted_at` set.
5. After that delete, creating a course with code `JAVA-101` succeeds, while creating a second live `JAVA-101` answers `409`.
6. A course with an unknown `instructorId` answers `400`.
7. The integration tests run against PostgreSQL in a container, not an embedded database.

## Suggested steps

1. Add `spring-boot-starter-data-jpa`, `spring-boot-starter-flyway`, and at runtime `org.flywaydb:flyway-database-postgresql` and `org.postgresql:postgresql`. For tests add `spring-boot-starter-data-jpa-test`, `spring-boot-testcontainers`, `testcontainers-junit-jupiter` and `testcontainers-postgresql`.
2. Write the first migration. A partial unique index lets a code be reused after a soft delete:

```sql
CREATE TABLE course (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code VARCHAR(20) NOT NULL,
    title VARCHAR(120) NOT NULL,
    description VARCHAR(2000),
    level VARCHAR(20) NOT NULL,
    instructor_id BIGINT NOT NULL REFERENCES instructor (id),
    deleted_at TIMESTAMP WITH TIME ZONE
);

CREATE UNIQUE INDEX course_code_live_uq ON course (code) WHERE deleted_at IS NULL;
CREATE INDEX course_instructor_idx ON course (instructor_id);
```

3. Configure the application. The password comes from the environment. Keep `V1000__test_data.sql` in `src/main/resources/db/testdata`, outside the default migration folder, and let only the `local` profile and the tests add that folder with `spring.flyway.locations=classpath:db/migration,classpath:db/testdata`:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/catalog
spring.datasource.username=catalog
spring.datasource.password=${DB_PASSWORD}
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
```

4. Map `Course` with a lazy `@ManyToOne` to `Instructor`, and give it the soft delete annotations. Hibernate then turns `delete` into an update and filters deleted rows out of every query on the entity:

```java
@Entity
@Table(name = "course")
@SQLDelete(sql = "UPDATE course SET deleted_at = now() WHERE id = ?")
@SQLRestriction("deleted_at IS NULL")
public class Course {
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "instructor_id")
    private Instructor instructor;
    private Instant deletedAt;
    // id, code, title, description and level omitted
}
```

5. In `CourseRepository`, redeclare the paged finders with `@EntityGraph(attributePaths = "instructor")`; sort by title and then id so pages are stable. Map entities to response records inside the store, inside its transaction, so lazy data is never read after it closes.
6. Map the unknown instructor to an exception your advice turns into `400`. Also map `DataIntegrityViolationException` to `409`: the service check is a courtesy, the unique index is the guarantee when two requests race.
7. Test the repository against a container. Slices import only their own auto-configuration, so name Flyway explicitly:

```java
@DataJpaTest
@ImportAutoConfiguration(FlywayAutoConfiguration.class)
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
@TestPropertySource(properties = "spring.flyway.locations=classpath:db/migration,classpath:db/testdata")
class CourseRepositoryTest {
    @Container
    @ServiceConnection
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:17-alpine");
}
```

The container class in Testcontainers 2 is `org.testcontainers.postgresql.PostgreSQLContainer`, the test annotations come from `spring-boot-testcontainers`, and the slice annotations from `org.springframework.boot.data.jpa.test.autoconfigure` and `org.springframework.boot.jdbc.test.autoconfigure`.

## Stretch goals

- Add `Topic` with a many-to-many table and load topics for a page without an N+1 pattern.
- Add a `version` column and optimistic locking, and map the conflict to `409`.
- Add `created_at` and `updated_at` columns through a migration.

## Common mistakes

- Setting `ddl-auto=update` so Hibernate edits the schema. Nobody reviews that change and production drifts from the repository; use migrations and `validate`.
- Reading a lazy relationship in the controller after the transaction ended, then "fixing" it by leaving Open Session in View on.
- Editing a migration that already ran. Flyway checks checksums and refuses; add a new version instead.
- Testing with an embedded database that differs from production, so partial indexes and types behave differently.

## In practice

The schema, the entities and the tests form a triangle: a migration changes the schema, validation fails until the entity matches, and the container test proves both against the real engine. Putting the guarantee (the unique index) in the database and the friendly message in the service gives both correctness and a good error.
