# Project: Secure Course API

This closing project adds an explicit security boundary to a course API: public health information, scoped reads, administrator writes, server-side method checks and tests that distinguish authentication from authorization. Build it locally with JDK 25 and Maven 3.9 or newer. Use Spring Boot 4 and Spring Security 7; the API accepts bearer access tokens and does not implement an authorization server or store browser sessions.

You need: Project: Course API, The Spring Security Filter Chain, Sessions Versus Tokens, JWT and OAuth 2 Resource Servers, CSRF and CORS, Method Security and Authorization Design.

## Goal

Create `secure-course-api` from the earlier in-memory course project. Keep its controller, service and repository separation. A learner can read courses with the proper scope, while an administrator can create and delete courses. Every rule is enforced by the API when called directly by any HTTP client. Keep persistence integration for a later extension so authorization tests have little setup.

## The contract

- `GET /api/public/ping` is public and returns a small status response without configuration details.
- `GET /api/courses` requires `SCOPE_courses:read`.
- `POST /api/courses` and `DELETE /api/courses/{id}` require `ROLE_ADMIN`.
- Every other route is denied unless it is explicitly added to the policy.
- A missing or rejected credential returns 401; an accepted credential without permission returns 403.

The role and scope names are independent contracts. An administrator token that has no read scope does not automatically satisfy the read rule. If the product wants that inheritance, declare and test it instead of assuming that the word administrator grants every authority.

## Dependencies and configuration

Use the Boot-managed `spring-boot-starter-webmvc`, `spring-boot-starter-validation` and `spring-boot-starter-security-oauth2-resource-server`. Add the matching web MVC, security and resource-server test starters in test scope. Keep versions under the Boot parent.

Configure an issuer URI and an audience for a real deployment. Use an identity provider you control; the host below is deliberately nonfunctional example configuration:

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.example.com/issuer
          audiences: course-api
```

For automated tests, supply a test-only decoder using an RSA public key generated by the test fixture. Configure issuer, audience and timestamp validation on that decoder too. A custom decoder replaces Boot's decoder configuration, so the properties alone cannot supply validators that the custom bean forgot.

## Suggested steps

1. Add the dependencies and a `SecurityFilterChain`. List the public rule first, the scoped GET rule second, administrator writes next and `denyAll` last.
2. Set `SessionCreationPolicy.STATELESS`. Disable CSRF only for this bearer-header API, which accepts no cookie or HTTP Basic authentication. A future session-based browser endpoint needs its own CSRF design.
3. Create a `JwtAuthenticationConverter` that combines the authorities from the default `JwtGrantedAuthoritiesConverter` with role authorities from a trusted `roles` claim. Prefix roles with `ROLE_` and preserve `SCOPE_` authorities. Reject malformed claim values rather than coercing arbitrary objects into permissions.
4. Enable method security and protect the create and delete service methods with `@PreAuthorize("hasRole('ADMIN')")`. An external call must pass through the Spring proxy; a direct `new` or self-invocation does not prove this protection works.
5. Keep security configuration outside the controller. Its methods still translate HTTP and delegate to the service.
6. Exercise the API directly with an HTTP client. Send bearer credentials only to the intended API, verify the authentication challenge on 401, and distinguish it from an authenticated caller’s 403. Keep local access tokens out of source control.

## Acceptance criteria

1. An unauthenticated request to ping succeeds, while listing courses returns 401 with a bearer authentication challenge.
2. A caller with the read scope can list courses. An authenticated caller without it receives 403.
3. An administrator can create and delete. A learner with only the read scope cannot perform either write.
4. The custom authority converter preserves both a token's scopes and its administrator role.
5. An otherwise valid, locally signed token with the correct issuer and audience can read courses through an actual `Authorization: Bearer` header.
6. Expired tokens, tokens from another issuer, tokens for another audience and tokens signed by another generated key each receive 401.
7. A test calling a protected service through its injected bean fails without administrator authority, proving method security rather than only URL security.
8. An unlisted endpoint is denied. No token or private key is committed, and no production decoder uses the generated test key.

## Two kinds of security test

MockMvc's `jwt()` request postprocessor is useful for authorization rules. It places an authenticated principal into the test request without verifying a JWT signature. Pass explicit authorities, or invoke the application's authority converter, to test the intended permission mapping.

It does not prove the decoder rejects a bad token. The second group must send a signed token in the real header and let the configured decoder verify it. Generate an RSA key pair in the test process, sign test claims, and keep the corresponding public key in a test configuration only. Choose expiration values comfortably outside the validator's clock-skew allowance when testing expiry. Run both groups with `./mvnw test`.

## Common mistakes

- Using `jwt()` for every test and claiming that signatures, issuer and expiry were verified. Those require the actual decoder path.
- Replacing the scope converter with a role converter, so read permissions vanish. Combine the authority collections deliberately.
- Disabling CSRF on an application that also accepts browser cookies. Revisit the policy when adding any automatically sent credential.
- Trusting a hidden button or client-side permission flag. Exercise protected endpoints directly and prove that the API rejects unauthorized calls.

## In practice

Keep the policy readable enough to audit in one file and maintain a table of public, read and write operations beside its tests. Each new endpoint needs an explicit access decision. Use generated credentials only for local tests, obtain real access tokens through the identity provider and keep authentication failures distinct from forbidden operations in client behavior and monitoring.

## Check yourself

1. Which test proves that a forged signature is rejected, and why does a jwt postprocessor test not prove it?
2. Why must a role converter preserve scope authorities when URL rules depend on them?
3. What changes in the CSRF design if the browser starts authenticating with a session cookie?
