# N+1 Queries and Batching

The most common performance bug in backend code generated by humans and assistants alike looks innocent:

```ts
const posts = await db.query('SELECT * FROM posts LIMIT 50');
for (const post of posts) {
  post.author = await db.query('SELECT * FROM users WHERE id = $1', [post.authorId]);
}
```

One query for the list, then one per item: **N+1** queries. With 3 rows in development it takes 5 ms. With 50 rows in production and 2 ms of network latency per round trip, the endpoint spends 100 ms just waiting, and it gets worse with every nested relation (posts → comments → authors). Frontend developers know the same shape as request waterfalls.

## Three fixes

**1. A JOIN**: one round trip, the database does the matching.

```sql
SELECT p.*, u.name AS author_name
FROM posts p LEFT JOIN users u ON u.id = p.author_id
LIMIT 50;
```

**2. Two queries, matched in memory** (what ORMs do for `include`):

```ts
const posts = await findPosts();
const ids = [...new Set(posts.map((post) => post.authorId))];
const users = await findUsersByIds(ids);
const byId = new Map(users.map((user) => [user.id, user]));
const feed = posts.map((post) => ({ ...post, author: byId.get(post.authorId) ?? null }));
```

Joins duplicate the parent columns for each child row (a post with 100 comments repeats the post 100 times), so for one-to-many relations two queries are often cheaper. Note the `Map`: rows come back in any order, and missing ids are simply absent.

**3. A DataLoader**, when the code that needs the data is spread across functions (GraphQL resolvers, nested serializers, service methods) and you cannot collect the ids in one place.

## How a DataLoader works

```ts
const authors = new DataLoader(async (ids: number[]) => {
  const rows = await findUsersByIds(ids);
  const byId = new Map(rows.map((user) => [user.id, user]));
  return ids.map((id) => byId.get(id) ?? null);
});

const feed = await Promise.all(posts.map(async (post) => ({ ...post, author: await authors.load(post.authorId) })));
```

Each `load(id)` returns a promise and puts the id in a queue. The loader schedules a single flush for later in the same tick (a microtask), so every `load` made synchronously, here by `map`, lands in one batch. The batch function must return one result per key, **in key order**. The loader also deduplicates: loading the same id twice returns the same promise.

It is the event loop you already know from the browser put to work: synchronous code queues requests, the microtask after it sends them together.

## Pitfalls

- **Cache lifetime**: a DataLoader's cache is a per-request memo, not an application cache. Create loaders per request (for example in the GraphQL context); a global loader serves stale data and can leak one user's data to another.
- **Order and gaps**: forgetting to reorder rows or to fill missing ids shifts every result by one, and authors get attached to the wrong posts.
- **Batches split by awaits**: a `load` that happens after an unrelated `await` may fall into a later batch. Real DataLoader waits a little longer (after `process.nextTick`) to catch more keys; still, check the query log.
- **Huge `IN` lists**: batch 10 000 ids and the query itself becomes slow; cap batch sizes (`maxBatchSize`).
- **ORMs hide it**: `post.author` lazy loading (TypeORM relations, Sequelize getters, Rails-style ORMs) issues a query per access. Ask for eager loading (`include`, `with`, `relations`).

## Detecting it

Log or count queries per request in development, use the ORM's query logging, or an APM trace (OpenTelemetry) where N+1 shows up as a staircase of identical spans. Integration tests can assert the query count, as this lesson's tests do.

## When to choose it

| Situation | Choose |
| --- | --- |
| One endpoint, known shape, one-to-one relation | JOIN |
| One-to-many relation, or reusing repository methods | two queries + `Map` (or ORM eager loading) |
| GraphQL resolvers, deeply nested or reusable data access | DataLoader per request |
| Same data read by many requests | an application cache (next lesson), not a DataLoader |

## Working with AI

Assistants often write the loop version because it reads naturally. Ask for "no queries inside loops; fetch relations with one query per relation" or "use DataLoader per request in the GraphQL context". Review checklist:

- No `await` on a query inside `for`, `map` or a resolver that runs per item, unless it goes through a loader.
- Batch functions return results in key order with `null` (or an `Error`) for missing keys.
- Loaders are created per request, never at module level.
- ORM relations are eager-loaded where the response needs them; lazy relations are not accessed in loops.
- There is a query count or a trace to prove the endpoint runs a constant number of queries.
