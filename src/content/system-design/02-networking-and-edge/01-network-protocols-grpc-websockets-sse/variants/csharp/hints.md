Both methods treat the stream as lines. In `FormatEvent`, a line break inside `Data` would end the field early, so every line of the payload needs its own `data:` field; a line break inside `Id` or `Event` has no safe encoding, so reject it before writing anything.
---
In `ParseEvents`, keep three variables outside the loop: the data buffer, the event type and the last event id. `stream.Split('\n')` gives the lines; the piece after the final `'\n'` is never followed by an empty line, so it can never dispatch, and `stream.Split('\n')[..^1]` leaves it out. Write `'\n'` yourself in both methods: `AppendLine` and `Environment.NewLine` write `"\r\n"` on Windows.
---
`message.Data.Split('\n')` gives the payload lines (`"".Split('\n')` is `[""]`, one empty line), and `message.Id?.Contains('\n') == true` checks `Id` (the same for `Event`). Pass only the message to `new ArgumentException(…)`: the constructor that also takes a parameter name appends ` (Parameter '…')` to `Message`. For a field line, `line.IndexOf(':')` finds the first colon: the field is what comes before it, the value what comes after, minus one leading space. On an empty line, emit only when the buffer is not empty, drop its final `'\n'` (`data.ToString(0, data.Length - 1)` on a `StringBuilder`), then reset the buffer and the event type in both cases, but never the last event id.
