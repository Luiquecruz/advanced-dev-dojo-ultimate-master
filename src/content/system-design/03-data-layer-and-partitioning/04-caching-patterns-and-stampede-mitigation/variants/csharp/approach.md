1. Separate the two kinds of state: finished values with an expiry, and loads still running. A stampede happens in the gap between "the entry expired" and "the new value arrived", so that gap needs its own record per key.
2. Make the in-flight record visible before the first `await`. Code here runs on a single thread, so other callers only run while your method is paused at an `await`: the task must be in the dictionary in the same call that starts the load. Awaiting a task that is already complete does not pause at all, so the code after that `await` also runs before the method returns.
3. Decide what happens when the load finishes: success stores the value with a jittered expiry and clears the in-flight record; failure only clears it. Caching a failure would keep serving the error after the database recovers.
4. Jitter is computed once per stored entry, at the moment of storing, so keys loaded together still expire apart.
5. For invalidation, think about the race from the theory: a load that started before a write may return the old row. Forget the in-flight task, and let a finishing load touch the dictionaries only while its task is still the current one: that keeps the old row out of the cache and keeps a newer load shared by later callers.
6. Optional: think about a server that handles requests on several threads at once. There, two misses can check the dictionary at the same moment and both start a load, and a plain `Dictionary` is not safe to change from two threads, so guard both dictionaries with a `lock`, or keep the in-flight loads in a `ConcurrentDictionary` whose values are `Lazy<Task<TValue>>`.
